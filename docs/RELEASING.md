# Releasing `zkteco-protocol`

**State as of 2026-09-01:** published. `zkteco-protocol@0.4.2` is on the registry — one version,
zero dependencies, `latest`, maintainer `chukhali`. §0 through §2 are done: the account has 2FA,
the `npm-publish` environment gates the publish job on a review, and the trusted publisher is
configured against `release.yml` with `npm publish` as its only allowed action.

**What has still never run is the pipeline's own publish.** 0.4.2 was published by hand and
therefore carries no provenance attestation. §3 is the procedure; 0.4.3 is its first exercise and
the first evidence the OIDC half works at all.

**The first published version is 0.4.2, not 0.4.1.** 0.4.1's CLI never ran at all when installed
from a tarball on any platform but Windows: npm links a bin as a symlink, the entry guard compared
an unresolved `argv[1]` against a resolved `import.meta.url`, and `main()` was never called — exit
0, no report, no message. It was found by this pipeline's first dry run, on the first Linux
execution of the drill in this project's history, and fixed in `cdd4c51`. Publishing 0.4.1 would
have burned that version number on a package that did nothing.

Publishing is the owner's decision, not a task to be picked up — see
`docs/superpowers/plans/2026-09-01-continuing-past-v0.4.1-HANDOFF.md` §3.

## 0. One-time: the npm account

1. Create an account at <https://www.npmjs.com/signup> and verify the email.
2. **Enable two-factor authentication** (Account → Two-Factor Authentication, authenticator app).
   `npm trust` in §2 requires it, and granular access tokens with 2FA bypass are not accepted there.
3. Confirm the name is still free:

   ```bash
   npm view zkteco-protocol
   ```

   `E404 … is not in this registry` means free. Anything else means somebody took it and everything
   below stops.

## 1. The first publish is by hand, and it is irreversible

**Why by hand.** npm's trusted publishing cannot perform a package's *first* publish: a trusted
publisher can only be configured against a package that already exists on the registry. So the name
is claimed once from a terminal, and the pipeline takes every release after that.

**What irreversible means.** A version can be unpublished without contacting support only within
**72 hours** and only if nothing depends on it; past that the conditions tighten (no dependents,
under 300 downloads that week, sole maintainer). And a name-version pair is burned permanently —
npm's policy is explicit that once `package@version` has been used it can never be used again, even
after an unpublish. Unpublishing every version locks the name for a further 24 hours.

Run, from the repository root, on a clean checkout of `main`:

```bash
npm login                 # browser-based; 2FA challenge
pnpm install --frozen-lockfile
pnpm release:drill        # 11 checks, exit 0 — see §4 if it fails
npm publish --dry-run     # read the file list before it is permanent
npm publish --access public
```

The dry run should list exactly `dist/`, `README.md`, `LICENSE` and `PROVENANCE.md` — the `files`
field in `package.json`. If anything else appears, stop and fix `files` first.

**Run the publish in an interactive terminal, not through a tool or a script.** npm enrols a
security key (WebAuthn), not a TOTP app: there is no six-digit code, so `--otp` has nothing to be
given and the 2FA challenge has to reach a browser or Windows Hello. A non-interactive shell cannot
be prompted and fails with `EOTP`, whose message — "requires a one-time password from your
authenticator" — reads as a missing code rather than as a missing terminal.

Then check it landed:

```bash
npm view zkteco-protocol version
```

**This first version will have no provenance attestation.** Provenance is generated by npm from the
CI run's OIDC identity, so a publish from a laptop cannot have one. Versions published by the
pipeline from §3 onward will. The difference is visible on the package page, and it is expected
rather than a fault.

Note that the CLI has no `--help`; it takes a host. There is nothing useful to run against the
published package without either a device or the emulator, and the drill already exercised the
packed artifact end to end.

## 2. One-time: trusted publishing, and the environment

### 2.1 The trusted publisher on npm

On <https://www.npmjs.com/package/zkteco-protocol> → Settings → Trusted Publisher → GitHub Actions:

| Field             | Value             |
| ----------------- | ----------------- |
| Organization/user | `ChuKhaLi`        |
| Repository        | `zkteco-protocol` |
| Workflow filename | `release.yml`     |
| Environment       | `npm-publish`     |

There is also a CLI path, on npm 11.15.0 or later, with 2FA enabled — check
`npm trust github --help` for the current flags before relying on this line:

```bash
npm trust github zkteco-protocol --repo ChuKhaLi/zkteco-protocol --file release.yml --env npm-publish --allow-publish
```

**The trust is bound to the workflow filename.** Renaming `.github/workflows/release.yml` silently
breaks publishing until the trust relationship is updated to match. There is a comment saying so at
the top of that file.

### 2.2 The approval gate on GitHub

Repository → Settings → Environments → New environment → name it **`npm-publish`** → tick
**Required reviewers** and add yourself → Save.

Without this the `publish` job runs unattended the moment a `v*` tag lands. With it, the job waits
for a click that you make *after* the `verify` job has gone green — which is the whole reason the
workflow is two jobs rather than one. An environment approval gates a job, not a step; in a single
job it would have been requested before any test had run.

## 3. Every release after the first

1. Bump the version in **both** `package.json` and `src/index.ts` (`VERSION`).
   `test/smoke.spec.ts` asserts they agree, so a half-bump fails the suite rather than shipping.
2. Commit and push to `main`. **Look at the Actions tab.** CI was red for two days in this
   repository's history with nobody noticing; a green tick is worth checking and cheap to check.
3. Tag and push the tag:

   ```bash
   git tag v0.4.2
   git push origin v0.4.2
   ```

4. The `verify` job runs: typecheck, build, test, the tag-equals-version assert, and the drill.
   The tag must be exactly `v` plus `package.json`'s version, in plain semver. **A prerelease tag
   such as `v0.5.0-rc.1` is refused** — publishing an rc as `latest` is a real footgun and the
   dist-tag handling that would prevent it has never run. Build it the day an rc is actually wanted.
5. GitHub asks for the `npm-publish` approval. Approve it.
6. The `publish` job publishes to npm and then creates the GitHub Release from the tag with
   generated notes.

**A dry run** — Actions → Release → Run workflow, leaving `dry_run` ticked — runs `verify` and
stops. It proves everything except the registry handshake: OIDC authentication cannot be exercised
without a real publish.

## 4. When something fails

- **`verify` red.** Nothing was published. Fix, then move the tag:
  `git push --delete origin v0.4.2 && git tag -d v0.4.2`, and tag again.
- **`npm publish` failed.** An npm publish is all-or-nothing, so the version is not on the registry.
  Re-run: Actions → Release → Run workflow, select the **tag** as the ref, untick `dry_run`.
- **Publish succeeded, `gh release create` failed.** The package is live and the Release is missing.
  This is why the publish runs first — the reverse would announce a version nobody could install.
  Fix it by hand and do not re-run the publish step; that version number is spent:

  ```bash
  gh release create v0.4.2 --title v0.4.2 --generate-notes --verify-tag
  ```

- **The published tarball is wrong.** It cannot be replaced. Publish a new patch version, and
  deprecate the bad one (`npm deprecate zkteco-protocol@0.4.2 "…"`) rather than unpublishing.
- **The drill fails.** It prints what it expected, what it found, and the temp directory it left
  behind. `.claude/skills/release-drill/SKILL.md` explains how to read a failure. Its expected
  values (`SN-PACKTEST-001`, `MB360`) are duplicated from `tools/emulator-serve.ts` and must be
  changed together — if they drift, the redaction checks search for a string the device never sends
  and pass forever.

## 5. What this pipeline does not prove

Stated because this project's signature defect is a check that reports more than it establishes.

- **The publish job rebuilds.** It publishes a build of the same commit with the same frozen
  lockfile that the drill ran against — not literally the bytes the drill installed. What the drill
  establishes is that a build of this commit packs, installs with zero transitive dependencies, and
  produces a correctly redacted report. One data point against this being a real gap: 0.4.2's
  published tarball has shasum `fd2920178c1059d013ec5ae96dd7987c0707f37e`, which a fresh local
  `npm pack` of the same commit reproduces exactly. That is one sample on one machine, not a
  determinism guarantee — but the gap is narrower than this bullet used to imply.
- **No CommonJS TypeScript consumer is ever typechecked against `dist/index.d.cts`.** Nothing in
  the drill or the suite compiles a `require()`-style consumer under `module: node16`. What is
  actually asserted is narrower: `test/smoke.spec.ts` checks that the file exists and that the
  `exports` map points `require.types` at it. A `.d.cts` that exists and is wrong — or right for a
  shape no consumer uses — passes every check here.
- **The release job runs one OS and one Node version** (ubuntu-latest, Node 24). The 2×3 platform
  matrix stays CI's job on `main`, which is why step 2 of §3 says to look at it.
- **A dry run cannot exercise OIDC.** The first tagged release is the first evidence the
  authentication half works at all.
- **The drill now runs on Linux, and the first time it did it found a shipped defect.** Every green
  run before 2026-09-01 was on Windows, and the platform it had never been run on was the one where
  the CLI did not work. Run 33476872217 is the first green Linux drill. What that says about any
  check here: a check that has only run in one environment has established something about that
  environment and nothing else.
- **No physical ZKTeco device has ever been connected to this library.** Publishing changes nothing
  about that. Keep the README's compatibility table honest.
